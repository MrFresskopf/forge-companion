# RAPT Brew native Data-Stream migration

## Decision

Use RAPT Brew's native **Data Stream** for a RAPT Pill instead of maintaining a
local RAPT-to-Brewfather relay. This removes the need to retain or distribute a
Brewfather Custom Stream logging ID in Forge Companion.

The direct `api.rapt.io` adapter remains an experimental, read-only **legacy
fallback** while the old RAPT portal is retired. It is not the target for new
installations.

## What this changes

```text
RAPT Pill -> RAPT Brew Data Stream -> Brewfather
```

This native path is separate from BrewForge. It does not populate a BrewForge
brew's readings, and it grants no telemetry-triggered control or actuator
permission in Forge Companion.

Forge Companion does not send a RAPT reading to Brewfather. A future Brewfather
reader must be based on one verified, sanitized response from the native data
stream; do not reuse the legacy RAPT Cloud proxy shape or infer field units.

## Setup in RAPT Brew

1. Log in to `brew.rapt.io`.
2. Open the profile menu, then **Manage Account**.
3. Open **My Integrations**.
4. Under **RAPT Brew Data Stream**, choose **Create Stream**.
5. Choose **Brewfather** and enter the Brewfather Integration ID generated by
   Brewfather.
6. Bind the stream to the intended Pill and attach the resulting Brewfather
   device to the active batch.

Keep the Integration ID out of source, command arguments, screenshots, and
issue text. Treat it as an integration credential.

## Cadence and safety gate

A standard free RAPT account has one Data Stream with telemetry every **six
hours**. This is sufficient for ordinary fermentation history but fails the
existing 90-minute Pill freshness warning and is unsuitable for trend-based
spunding, remote hop drops, or any other time-sensitive decision.

Do not retire the direct legacy reader for an operational workflow until the
actual native stream rate has been observed and a separate safety review has
accepted a freshness threshold for that rate. A subscription may offer higher
rates, but the rate must be verified from received timestamps rather than
assumed from an account tier.

## Acceptance check before changing consumers

For one fermentation, run both routes in parallel and compare only the values
shown in each service:

- the intended Pill is the source device;
- the Brewfather device has a timestamp, SG, and temperature;
- the received cadence is measured over enough points to expose gaps;
- timestamps and units are documented from the actual response, not inferred
  from a legacy endpoint;
- no automation uses the new route;
- the legacy RAPT API is retained until the comparison is accepted.

After that check, use the separate, read-only Brewfather adapter. It requires an explicit Brewfather
`deviceId` plus explicit `sg`, `c`, and `epoch-ms` declarations; it preserves the device as an
opaque Brewfather stream identifier, never as a RAPT UUID. It validates selected records atomically,
retains SG/temperature/RSSI, and deliberately does not infer battery or target-temperature units.
Do not build an Android UI scraper or a local RAPT-to-Custom-Stream sender as a substitute for the
native RAPT Data Stream.

## Current discovery command

Forge Companion now has the deliberately narrow first read-only slice. Store a
Brewfather API profile with a `batches:read` key, then run the command for the
completed batch that already shows Pill history:

```bash
forge-companion brewfather auth login
forge-companion brewfather readings-schema ACTUAL_BATCH_ID
```

The schema command makes exactly one readings request and returns only the
record count plus field names and JSON value types. It does not print readings,
timestamps, device names, or credentials. Use its output to establish the
native response shape before implementing a consumer.
